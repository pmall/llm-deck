Part 1 · The Foundation Model

Tokens: How Models Read

  • Training datasets are split into discrete sub-word units (tokens)
  • Tokens are how models ingest, index, and represent any textual input
  • A token is not a word, not a syllable, not a character — it is whatever the tokenizer learned was frequent
  • The same sentence costs a different number of tokens depending on the language it is written in
Demystifying LLMs 5

Part 1 · The Foundation Model

Autoregressive Generation

  • At each step, the model produces a probability distribution over its entire vocabulary — a score for every possible next token
  • The next token is then sampled from that distribution
  • The chosen token is appended to the text, and the whole process starts again for the following token
  • Sampling — not the model — is what makes the same prompt produce different answers

Reflexive Writing, Not a Knowledge Base

  • The model is not a structured query engine — there is no lookup, no record being retrieved
  • It performs “reflexive writing”, conditioned entirely by the input prompt
  • When the continuation is obvious, the result looks like knowledge — but the mechanism is the same one that continues any other sentence

Part 1 · The Foundation Model

Language Disparity in the Data

  • Massive imbalance in pre-training sets — roughly 80% English dominance
  • Consequences for everyone not working in English:
    • Quality gap — prose, vocabulary and factual coverage are visibly richer in English
    • Cost and context — the same text costs more tokens in most other languages, so it eats more of the context window
    • Cultural default — norms, references and examples skew towards English-language sources
    • Local knowledge — national regulations, administrative procedures and domain jargon are thinner in the data
  • Practical consequence: working in English and translating afterwards often beats working directly in another language — and the gap widens as the language gets smaller

Part 2 · Post-Training

In-Context Pattern Matching

  • Emergent capability to recognise and reproduce structural patterns found in the prompt itself
  • Nobody trained the model for this specific task, and nobody gave it an instruction — it continues the pattern because continuing is all it does
Demystifying LLMs 13

Part 2 · Post-Training

Instruction Tuning & Assistant Alignment

  • Instruction tuning — fine-tuning the base model on conversational datasets: instructions paired with the responses an assistant should give
  • Pattern reproduction again, this time at training scale — the pattern being learned is the assistant role itself
  • The result answers the instruction instead of continuing the text, with a stable persona and tone across turns
  • The base model was not refusing to help — it had no notion of being asked
Demystifying LLMs 14

Part 2 · Post-Training

Reinforcement Learning Horizons

  • Reinforcement learning — the model answers, the answer is graded, and training reinforces whatever scores well
  • RL on verifiable answers — automatic grading against known-correct results, over encyclopedic and factual datasets: this is what buys accuracy and factual consistency
  • RLHF — humans compare two candidate answers and keep the better one: this is what shapes tone, helpfulness and safety
  • Two distinct targets: what the model knows, and how it behaves
Demystifying LLMs 15

Part 2 · Post-Training

System 2 Thinking: Reasoning RL

  • Models are trained to generate internal scratchpad reasoning before emitting a response
  • The model learns to rephrase, explore strategies, notice mistakes, and self-correct internally
  • The visible answer is the tip of a much longer hidden process
Demystifying LLMs 16

Part 2 · Post-Training

Chat Is Stateless

  • There is no ongoing conversation on the model side — the model remembers nothing between two messages
  • Every new message re-submits the full history alongside it, on every API call
  • Direct consequence: KV cache — key-value caching stores the attention states already computed for the history, so the same text is not re-processed from scratch at every turn
  • Without it, every additional turn would be slower and more expensive than the last
Demystifying LLMs 17

Part 2 · Post-Training

Context Rot: The Long Conversation Trade-off

  • The KV cache makes long conversations cheap and fast — so nothing pushes you to ever start a new one
  • But reasoning performance degrades gradually as context size scales up: instructions given early get diluted, contradictions accumulate, attention spreads thin
  • The failure is silent — the model does not warn you that it is doing worse
  • Practical rule for daily use: a new topic deserves a new conversation; restate the goal when a thread gets long; keep only the documents that are still relevant

Part 2 · Post-Training

Grounding via Context Injection

  • Parametric memory — writing from what the model absorbed during training
  • Context grounding — composing a grounded analysis directly from user-provided documents inside the active prompt
  • Same model, same question: what changes is what is in the prompt

Tools and Agentic Loops

Part 3 · Tools and Agentic Loops

What Is an “Agent”? Nobody Quite Agrees

  • The word has no settled definition, which is why conversations about agents go in circles
  • Is the agent the model? The software around it? The combination? Vendors use the term for all three
  • What we can define precisely:
    • The LLM is the text and reasoning engine
    • The harness is the software built around it: the tools, the loop, the state, the interface
    • “Agent” is best treated as a degree, not a category — how much initiative the harness lets the model take between two human interventions
Demystifying LLMs 22

Part 3 · Tools and Agentic Loops

Tool Calling Foundations

  • If a language model can write text, it can write executable structured instructions for external API tools
  • The model does not run anything itself — it writes a request, and the surrounding software executes it and writes the result back
  • Which makes the conversation a three-party exchange: the user, the agent, and the system that answers the agent’s requests
  • Two of those three parties are usually invisible to the user
Demystifying LLMs 23

Part 3 · Tools and Agentic Loops

The Self-Referential Execution Flow

  • Instruction Message → Tool Response Message
  • The system interacts with itself, in an automated loop
  • Each tool response becomes new context, which conditions the next instruction, which triggers the next tool call
  • One question rarely means one tool call: the exchange repeats until the agent has what it needs

Part 3 · Tools and Agentic Loops

A Weekend in Paris

  • One request in plain language: “Plan me a weekend in Paris in two weeks, I like museums and I don’t want to walk more than twenty minutes between stops.”
  • What the agent has to go and fetch before it can answer anything:
    • Weather — the forecast for those specific dates, to decide what is indoors and what is outdoors
    • Places — museums and restaurants, with opening hours and closing days
    • Routing — actual walking times between candidate stops, to respect the constraint
  • None of it is in the model. All of it is fetched, then reasoned over.

Retrieval: Bringing Data In

  • RAG (retrieval-augmented generation), database querying, document and email search
  • The agent searches for what it needs, when it needs it, instead of being handed everything up front
  • Goal: automatically fetch dynamic context into the active prompt window
  • This is Slide 19’s grounding, made automatic — the agent attaches the document to itself

Part 3 · Tools and Agentic Loops

Acting Through APIs

  • Retrieval reads; APIs act
  • Anything with an API is reachable: send the email, create the calendar event, update the CRM record, open the ticket, publish the post, drive a 3D or CAD application to build a model
  • The same mechanism as Slide 23 — the model writes a structured request — only now the request changes something
  • Which makes the distinction that matters in practice: reversible actions vs. irreversible ones, and which ones you are willing to leave unsupervised
Demystifying LLMs 27

Part 3 · Tools and Agentic Loops

Computer Use: When There Is No API

  • When there is no API, the agent can use the software the way a person does: read the screen, move the pointer, click, type
  • Unlocks the long tail — legacy internal applications, unstructured web interfaces, anything nobody ever built an integration for
  • Slower, more fragile and more expensive than an API call: the interface can change, and the agent has to re-find its footing
  • The right mental model: not a new superpower, but a fallback for everything that was never made machine-readable
Demystifying LLMs 28

Part 3 · Tools and Agentic Loops

Code Execution

  • The agent writes code and runs it in a sandbox, then uses the result
  • “Why would I need code?” — because some things a language model is bad at, code is exact at:
    • Volume — apply the same treatment to 5,000 rows of a spreadsheet: the rows may well fit in the context window, but the model will not reason identically on row 4,000 and on row 12
    • Arithmetic — computing totals, deltas and rates exactly, rather than predicting plausible-looking numbers
    • Repeatability — the same script on next month’s file gives the same treatment, and can be audited line by line
    • Orchestration — looping over tool calls, chaining them, handling the failures
  • Structured data parsing and precise programmatic tool execution inside code environments

Part 3 · Tools and Agentic Loops

Dynamic Instructions (Skills)

  • Loading specific behavioural procedures, domain rules, and action templates on the fly, as needed
  • The key distinction from Slide 26: retrieval injects data; skills inject instructions — how to do the thing, not what the thing is
  • Typical contents: the house format for a client report, the validation checklist before anything is published, naming and filing conventions, the steps of the monthly close, the tone rules for external communication
  • Loaded only when relevant, which keeps the standing instructions short — and Slide 18 explains why that matters

Part 3 · Tools and Agentic Loops

The ReAct Loop

  • Iterative cycle: Think → Act → Inspect → Adjust, until task validation criteria are met
  • The combination is what works: reasoning to plan, tools to act on the real world, verification to check the result against the goal
  • Reasoning alone produces plausible plans; tools alone produce unchecked actions; only the loop produces a result that has been tested
  • The agent stops when the criteria are satisfied — not after a fixed number of steps

Software Engineering: The Ideal Sandbox

  • Code execution offers deterministic feedback loops: compilation outputs, unit tests, linters
  • The verification step of the loop is free, instant, and unambiguous — the test passes or it does not
  • This is why coding agents matured first, and why the same reliability is harder to reach on fuzzier tasks

Conclusion

The Operational Mindset Shift

  • Level 2, today: Prompt → Read answer → Spot error → Manually prompt a correction
  • Level 3, the shift: Define the target goal and validation criteria → the agent executes, inspects its own output, and self-corrects autonomously until the criteria are satisfied
  • What you supply: context, instructions, and the expected result
  • What you no longer supply: the exact instructions on how to do it
